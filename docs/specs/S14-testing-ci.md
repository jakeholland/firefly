# S14 · testing & CI (BUILD FIRST, with S13)

## Purpose
The merge referee. Agent PRs merge on green — so green must mean something.

## Deliverables
1. **Unit**: Unity via ctest. Convention: one test exe per module (`test_geo`, `test_crew`, …); test names `SNN_ACX_description`. `ctest --output-on-failure`.
2. **Golden screenshots**: `tests/golden/*.png` + `tests/run_goldens.sh` — renders every fixture headlessly, compares with `compare_png` tool (pixel diff, ≤0.5% threshold), emits side-by-side diff PNGs as CI artifacts on failure. `--update-golden` regenerates (deliberate commits only; PR diff shows PNGs).
3. **Sanitizers**: sim/unit builds compile with ASan+UBSan in CI; fuzz smokes (S03/S05) run 10k iters in CI.
4. **E2E** (`tests/e2e/`, pytest): compose up meshtasticd → crew_sim scenarios → ctl-socket assertions + screenshots. Scenarios v1: `test_dana_walk` (position flows to radar view state), `test_flare_reaches_feed` (renamed 2026-09-02 from `test_pulse_feed`/`test_pulse_reaches_feed` — PULSE is retired, see docs/specs/S04-firefly-protocol.md's Amendments), `test_text_roundtrip`. Runs nightly + on `e2e` label (docker too slow for every PR).
5. **GitHub Actions** `ci.yml`:
   - `build-test` (PR gate): Ubuntu, cache CMake deps, build sim, ctest, goldens, upload screenshot artifacts.
   - `esp32-build` (PR gate once S15 lands): espressif/idf docker, build-only.
   - `e2e` (nightly + label).
   - Branch protection expectation: PRs merge via `gh pr merge --squash --auto` after `build-test` green.
6. **`tools/new_module.sh`**: scaffolds module dir + include + test exe + CMake wiring so agents don't hand-copy boilerplate.

## Acceptance criteria
1. Fresh-clone CI run is green with the S13 skeleton (even before feature modules land — placeholder test passes).
2. A deliberately broken golden fails CI and uploads a visual diff artifact.
3. ASan catches a planted heap-overflow in a scratch test (verified once, then removed) — proving sanitizers are actually on.
4. e2e smoke passes against pinned meshtasticd image tag.

## Slices
a) ctest+Unity+ci.yml gate · b) goldens tooling · c) sanitizers+fuzz hooks · d) e2e harness+nightly.

## Amendments
- **2026-09-02, PR #TBD (`debt/ci-gates`) — CI gates hardening.** Four gaps closed:
  - **No timeout anywhere.** Neither ctest nor any GitHub Actions job had a timeout, so a hung test (a real hang class was just reproduced in the sim tests) would ride GitHub Actions' 360-minute *job* default before anything noticed. Two layers now: (1) `firmware/CMakeLists.txt` redefines `add_test()` — CMake auto-generates an underscore-prefixed alias (`_add_test`) for any built-in command shadowed by a function/macro of the same name, so the redefinition wraps every `add_test(NAME ... COMMAND ...)` call anywhere in the tree (core/meshclient/festpack/app/targets/sim, ~20 call sites) with a default `TIMEOUT` property (120 s, `FF_DEFAULT_TEST_TIMEOUT_SECONDS` cache var) without editing each call site. This is CMake-side deliberately, not `ctest --timeout` flags in ci.yml, because it protects a bare `ctest` run on a contributor's laptop too, where there is no GitHub Actions job wrapper at all. Verified by planting `while(1);` in `test_core`'s first test, rebuilding, and confirming `ctest` reports `***Timeout` at the configured budget instead of hanging (plant removed before commit; PR body has the full transcript). (2) `timeout-minutes: 20` added to every job in `ci.yml` and `e2e.yml` as a coarser second backstop for anything that hangs outside a registered ctest test (a script step, a dependency fetch stalling).
  - **`esp32-build` never existed.** S15 deliverable 7 / AC6 ("CI esp32 build green") was specified but never implemented — dozens of device-facing PRs merged on `ci.yml`'s sim-only gate alone. Added as its own workflow file, `.github/workflows/esp32.yml` (not a job folded into `ci.yml` — see that file's header for why), build-only via `espressif/esp-idf-ci-action` pinned to a commit SHA (`v1.2.0`), with `esp_idf_version: v5.3.5` pinned to match `firmware/targets/esp32s3/main/idf_component.yml`'s `idf: ">=5.3"` constraint and the maintainer's actual toolchain (`idf.py --version` on the maintainer's `~/esp/esp-idf` resolves to `v5.3.5-889-g7a911c980d6`). A 2-leg matrix builds BOTH `sdkconfig.defaults` alone (the honest fresh-checkout STAGE-1 bring-up build) and `sdkconfig.defaults;sdkconfig.ci` (the shipping config — see S15's own Amendments and `sdkconfig.ci`'s header). Deliberately **not** added to branch protection as a required check by this PR — the maintainer does that after watching it run green a few times.
  - **Sanitizers job never ran ffsim.** `ci.yml`'s `sanitizers` job only ran `ctest --test-dir build-asan`; goldens and the headless boot screenshot — the two things that actually exercise the render paths most likely to hit a heap issue — ran only against the plain (non-instrumented) `build/ffsim` in the `build-test` job. `run_goldens.sh` already accepted an explicit `$BUILD_DIR` override (see its own header comment, "Build-tree location (#55)"), so no script change was needed — the `sanitizers` job now also runs `run_goldens.sh` with `BUILD_DIR=.../build-asan` and a headless boot screenshot against `build-asan/ffsim`, both under `UBSAN_OPTIONS=halt_on_error=1`. Verified locally first: 72/72 golden fixtures passed under ASan+UBSan with zero findings, and the boot screenshot rendered cleanly.
  - **Two unrelated FetchContent caches.** `build-test` cached `firmware/build/_deps` and `sanitizers` cached `firmware/build-asan/_deps`, both drawing from the identical `FetchContent_Declare` sources (lvgl/unity/nanopb) in `firmware/CMakeLists.txt` but never sharing a cache. Chose a shared **restore-keys prefix** (`${{ runner.os }}-fetchcontent-`) over a single shared `_deps` path: `CMAKE_C_FLAGS` is a whole-tree setting, so `sanitizers` compiles every FetchContent'd dependency WITH `-fsanitize=address,undefined` too — the two `_deps` trees' *build* artifacts are not interchangeable, and a single shared path would make the outcome depend on which job's cache-save won the race (`actions/cache`'s first-writer-wins). The restore-keys prefix still lets a cold job warm-start from the other job's cached *source* clone (the slow/flaky part) while keeping each job's own exact-key save independent and correctness-preserving; CMake's own dependency tracking safely recompiles any object whose flags changed.
