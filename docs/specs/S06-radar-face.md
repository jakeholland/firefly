# S06 · app/radar — the Radar face

## Purpose
The hero screen: honest arrow to the selected crew member, whole-crew ring, three states. Mockups are the layout authority (412×412 circle; "Radar — live / stale / close range" artboards).

## State in, pixels out
Radar renders `ff_radar_view_t` computed in core (`core/src/ff_radar.c`) from crew + geo + clock:
```c
typedef enum { RADAR_LIVE, RADAR_STALE, RADAR_LOST, RADAR_CLOSE, RADAR_NOFIX, RADAR_NOSEL } radar_mode_t;
// DRIFT GUARD (PR #12 review finding #5): until this lands in
// core/include/ff_radar.h, firmware/app/include/ff_app_state.h's
// ff_app_radar_t mirrors this struct field-for-field under a different
// type name (two anonymous structs with an identical member list are
// still distinct C types under the same typedef name — reusing
// ff_radar_view_t there would be a redefinition hazard the moment a
// screen file includes both headers). Whoever implements this slice:
// either (a) delete ff_app_radar_t and point ff_app_state_t.radar at
// the real ff_radar_view_t below (preferred), or (b) if both must
// coexist a while longer, update ff_app_state.h's copy in the same
// change as any field added/removed/retyped here.
typedef struct {
  radar_mode_t mode;
  float arrow_deg;            // smoothed screen rotation
  bool  arrow_valid;          // false in CLOSE/NOFIX/NOSEL
  char  name[16]; char dist_str[12]; char age_str[12];
  int8_t trend;               // −1/0/+1 (CLOSE mode hot/cold)
  struct { float ring_deg; char initial; uint8_t color_idx; bool stale; } dots[FF_CREW_MAX];
  uint8_t n_dots;
  char clock_str[6]; int8_t batt_pct; bool mesh_ok;
} ff_radar_view_t;
void ff_radar_compute(ff_radar_view_t *v, ff_crew_t *crew, float heading_deg,
                      ff_latlon_t my_pos, bool my_pos_ok, uint32_t now_ms);
```
- Mode: NOSEL if no paired member; NOFIX if `!my_pos_ok` or heading invalid (shows zone-chips per S02 data, arrow hidden, "NO FIX · RADIO ONLY" label); CLOSE per S02 predicate; else LIVE/STALE/LOST from freshness.
- Arrow smoothing: exponential, time-constant 250 ms, wrap-aware (`ff_geo_angdiff_deg`). Update rate 10 Hz.
- Crew ring dots at each member's bearing (heading-relative); stale members dashed.

## Rendering (LVGL, `app/screens/scr_radar.c`)
- Layout constants transcribed from mockup (arrow 140 px glyph rotated; name 21 px; distance 36 px mono; chip pill). Colors from `app/theme/ff_theme.h` (amber #FFC66B, stale #FFB454, live-green #9BE07B, crew palette pink/teal/violet/green). Fonts: Montserrat-LVGL stand-ins v1, custom fonts tracked as issue.
- STALE: dashed arrow at 28% opacity, amber rim tint, "LAST SEEN …" chip (12 px equivalent).
- LOST (a real, aged fix — distinct from a paired member who has never sent one at all, see `ff_radar.h`'s RENDERER CONTRACT): must read as a *different* state from STALE, not a dimmer copy of it — no rim tint, an outline-only ("ghost") arrowhead rather than a filled one, distance prefixed with `~` to signal imprecision, and a chip in a muted/dark color distinct from STALE's bright amber (PR #16 UX review, orchestrator ruling: "STALE says this is a few minutes old, LOST says do not trust this").
- CLOSE: arrow → three pulsing rings (LVGL anim, 1.2 s period), "~Nm" big, trend chip, FLARE button (48 px high, full hit area).
- Status bar alert color: mesh-loss ("NO MESH") and low battery both render in the amber alert color (`FF_THEME_COLOR_STALE_AMBER`), not flat chrome grey — losing the mesh radio breaks the puck's entire purpose and must look at least as alarming as a low battery, not less (PR #16 UX review finding #6). Low-battery threshold is `FF_THEME_BATT_LOW_PCT` (`app/theme/ff_theme.h`) = 15% — a product-judgment call, not derived from S02/S03 (neither defines a battery threshold), documented here so this is its one source of truth.
- **Layout resolution (`app/screens/radar_layout.h`/`.c`).** Crew ring dots (and the arrow) are heading-relative and can land anywhere regardless of what fixed chrome (chips, buttons, the name/distance block, the status bar, the page-dot row, the ring stack) happens to occupy that bearing. A single reserved-region registry is built once per render (every fixed chrome rectangle, no exceptions), and every movable element resolves against the WHOLE registry:
  - **The arrow** resolves by *shortening* along its true bearing (a 1-D search over length, testing the full head — tip + both base corners — against the registry union fresh at each step) until it clears every reserved rectangle or hits a length floor. It never moves off-axis — an arrow may go short, it must never point somewhere it doesn't mean.
  - **Each ring dot** resolves by searching for the nearest *clear angle* at the ring's fixed radius (a 1-D search over angle, same union-tested-per-candidate approach). Iterative "push out of whichever rectangle you're in" was tried first and rejected: when two reserved rectangles overlap each other (which they legitimately do, e.g. CLOSE's ring stack and its status bar/name-chip rects), push-out-of-A can land a point inside B and push-out-of-B lands it back inside A — an oscillation a fixed pass cap just stops mid-way through, still colliding. A fresh full-registry test per candidate has no such failure mode: there's nothing to oscillate between, only "does this candidate work, yes or no."
  - **Dot clustering, never hiding.** If two or more dots' resolved positions still land within one dot-diameter of each other (crew converging on nearly the same bearing — an ordinary festival scenario, not a hypothetical), they are merged into a single **cluster marker** showing the member count (e.g. a dot showing "3" instead of an initial, in a neutral surface color rather than any one member's crew color) rather than any of them being hidden. Silently dropping a *known* crew member from the ring is an honesty failure in the same family CLAUDE.md's "never fake freshness, positions, or times" rules out — the app knows they're there; the screen must say so, even coarsely. Every dot is always accounted for in exactly one marker. *(Marker **styling** — "in a neutral surface color rather than any one member's crew color" — was superseded on 2026-08-23; see Amendments. The clustering rule itself is unchanged.)*
  - See `radar_layout.h`'s doc comment for the full algorithm and its termination bounds, and `app/screens/tests/test_radar_layout.c` for the geometry-level regression coverage (a full tenth-of-a-degree sweep per mode, not a golden-PNG proxy) — PR #16 UX review round 3 and code review round 2.
- Input: tap center = cycle selected member; swipe left/right = face nav (owned by S06's shell `scr_nav.c`: three faces + page dots); long-press = settings (S11).

## Acceptance criteria (compute = unit; render = golden PNG)
1. Mode truth table (10 rows: fresh/stale/lost/close/nofix/nosel × pos/heading validity) exact.
2. Smoothing: step 0→90° reaches ≥81° at 600 ms, no overshoot >2°; 350→10° goes through 0, not 180.
3. Dots: 4-member fixture → bearings/colors/stale flags exact; unpaired members excluded.
4. Golden screenshots: fixtures `radar_live.json`, `radar_stale.json`, `radar_close.json`, `radar_nofix.json` render pixel-identical to goldens (allow ≤0.5% differing pixels for AA).
5. Tap-cycle changes selection; swipe changes face (sim input-injection test).
6. Compute is allocation-free and runs <1 ms on host (sanity perf bound).

## Slices
a) ff_radar_compute + tests · b) shell/nav + theme · c) live+stale render + goldens · d) close+nofix render + FLARE button hook (fires S10 callback).

## Amendments

- **2026-08-23, issue #18 / PR #41 (cluster marker styling — supersedes the "neutral surface color" clause of the "Dot clustering, never hiding" bullet above; that bullet's *clustering rule* is untouched and still binding).** The count digit now sits inside a ring divided into one **wedge per clustered member, in that member's own crew color**. The original styling reasoned from a true premise — no *single* crew color applies honestly to a mixed group — to a conclusion that cost more than it saved: white-outline-plus-digit is the visual vocabulary of a notification badge, while every other crew element on this ring is color + letter, so the one marker meaning "several of your friends are standing together over there" was the one marker that read as generic chrome. Giving each member their own wedge answers the honesty objection instead of trading it away — no color is claimed *for the group* — and the marker now says *which* friends, which the neutral version could not say at all.

  **Per-member freshness is carried by wedge THICKNESS, not opacity, and this is load-bearing.** A stale member's wedge is drawn at the lone "ghost" dot's own 2px width **and its own `LV_OPA_70`**, in that member's crew color; a current member's at 6px and full opacity. (An earlier draft of this amendment said "at full crew color", which the code review correctly flagged as not matching the code — the point is to mirror the ghost dot's `border_opa` exactly, so 70% is the right value and the amendment text was the thing that was off. What changed versus the rejected first implementation is that opacity is no longer carrying the *distinction* — thickness is.) The first implementation (PR #41, first pass) instead crushed a stale wedge's opacity to 40%, which the UX review rejected on two measured grounds. It is *relative* — a dimmed wedge only reads as dimmed beside a bright one, so a cluster in which **every** member is stale rendered indistinguishably from a live one, and the measured contrast of the dimmed wedge against the puck background was 2.2:1 (against 12.5:1 for a fresh green wedge). And it contradicted the idiom the rest of the face teaches: a lone stale dot is *hollow and bright*, so "hollow/thin means old" must hold here too — a dark wedge on a near-black puck reads as *dropping out*, a different and scarier fact than the true one. Thickness is absolute: it needs no neighbour to compare against.

  **The count digit follows the marker's overall freshness** — full `FF_THEME_COLOR_INK` while at least one member is current, `FF_THEME_COLOR_MUTED` when none are. Otherwise the brightest, crispest element on a marker where nothing is current is the number, i.e. the thing that most looks like a hard fact.

  Geometry (equal gapped slices, first wedge starting at 12 o'clock so a pair splits left/right) is `radar_layout_cluster_wedges` in `app/screens/radar_layout.h`/`.c`, unit-tested alongside the resolver; `scr_radar.c` only paints the angles it returns. That function **refuses (returns -1) rather than emit a partial ring** when a cluster exceeds the caller's buffer — a short count would let it satisfy its own signature by hiding a member. The marker keeps its exact one-dot-diameter footprint, so no collision geometry changes. Fixtures: `radar_cluster.json` (four members, one stale — the mixed case) and `radar_cluster_stale.json` (four members, all stale — the case the first pass got wrong).

- **2026-08-23, issue #18 / PR #41 (KNOWN GAP, not fixed here — crew colors run out before crew does).** `ff_theme.h`'s crew palette has **four** colors and `FF_CREW_MAX` is **eight**, with `ff_theme_crew_color()` wrapping modulo 4. By pigeonhole, a cluster of five or more *guarantees* at least two members render in the same color, and two same-colored adjacent wedges read as one continuous hoop with a thin notch — shape says one friend, only the digit says two. Nobody is hidden (the digit and the wedge count stay correct), so this is not an honesty failure, but it is a legibility one. The collision is pre-existing; what is new is that this amendment makes crew color **load-bearing for telling people apart inside a marker**, which turns a cosmetic clash into a miscount. Two further observations from the same review, recorded so a fix is designed against all three: past roughly five members the segmented ring reads as a **loading spinner** rather than as people, and the reviewer's own priority was explicit — *"I don't care about the count; 'several, that way' is the entire message I need"*, which suggests the fix may be to stop drawing a wedge per member above some threshold rather than to extend the palette to eight. Needs its own issue and its own fixtures (nothing above four members is covered by a golden today).

- **2026-08-24, S16 slice c1 (input ownership — supersedes the Input line's "swipe left/right = face nav (owned by S06's shell `scr_nav.c`)" and slice (d)'s "FLARE button hook (fires S10 callback)").** Face navigation is owned by `app/ff_route.c` + `ff_shell_intent` (S16); `scr_nav.c` is chrome only. Interactive controls hand a semantic intent up through the emit seam (`app/include/ff_intent.h`) and the shell decides — no screen file decides which face is active, ever. As of S16c1 the long-press-Settings hook's *callback* emits `FF_INTENT_OPEN_SETTINGS` (which the shell deliberately rejects until S11 slice b ships a Settings renderer — see `ff_shell.c`'s judgment-call note) — but **the physical gesture does not yet reach that callback** (PR #54 review, measured with `lv_indev_search_obj`): the full-size tileview covers the puck, LVGL objects are clickable by default, and no event bubbling is configured, so an on-glass press resolves to the tileview and the puck's handler only fires from a directly-delivered event. Until slice c3 the long-press is doubly inert — unreachable at the input layer *and* rejected at the shell. Three residuals therefore land with their own S16 slices, recorded so this entry doesn't overclaim: routing the physical long-press to the seam (c3, which owns the tileview's input handling), the FLARE button still calling `ff_flare_send_begin` directly until slice c2 converts it to `FF_INTENT_FLARE_START`, and the tileview still performing the physical swipe gesture itself until slice c3 disables `LV_DIR_HOR` scrolling and routes the gesture through `FF_INTENT_SWIPE` (S16 AC2 cannot fully hold until it does). Criterion 5's "swipe changes face" is then a statement about `ff_route_swipe` via the seam, not about `lv_tileview`.

- **2026-08-24, S16 slice c3 (closes the residuals above).** All three land: `scr_nav.c`'s three tiles now pass `LV_DIR_NONE` to `lv_tileview_add_tile` (were `LV_DIR_HOR`), so the tileview never natively scrolls, and a horizontal drag is resolved as an LVGL `GESTURE` instead and translated to `FF_INTENT_SWIPE` — S16 AC2 now holds against real input, not merely at the `ff_route_swipe` unit level. Long-press reachability: the tileview and its tiles carry `LV_OBJ_FLAG_EVENT_BUBBLE`, so an unhandled `LONG_PRESSED` bubbles tile → tileview → puck; content buttons (FLARE, ...) deliberately do NOT carry that flag, so a long-press on one of those still can't misfire `OPEN_SETTINGS` — the exact failure mode the c1 entry's own TODO warned a blanket flag would cause. (One correction to the c1 entry's own diagnosis, found implementing this: LVGL's `LV_OBJ_FLAG_GESTURE_BUBBLE` is already set on every object with a parent by default — `lv_obj.c`'s constructor — so the swipe fix is achieved by *clearing* it on the tileview, which is what stops the gesture-resolution walk there, not by adding it to the tiles as the c1 entry's phrasing might suggest.) `lv_indev_search_obj` still resolves an on-glass press to the tileview/tile, not the puck — that half of PR #54's finding was never the bug; `test_scr_intent.c`'s reachability test asserts this explicitly rather than assuming it. Verified with a real `lv_indev_t` (press → move steps → release, and a bubbled `LONG_PRESSED` sent to the actually-resolved object), not a synthesized event delivered straight to the puck.

- **2026-08-24, issues #33/#47 (position honesty round — adds `RADAR_PLACE` to `radar_mode_t`, and `dist_str`/`dist_imprecise` treatment for degraded-precision positions; neither is in this spec's original sketch).**
  - **#33 — asserted positions leave the freshness axis entirely.** A landmark's fixed position re-broadcasts on the ordinary interval forever, so freshness alone could never age it into STALE/LOST (the one signal this project relies on to stop trusting a reading). `ff_crew_freshness` (`core/include/ff_crew.h`) gained `FF_FRESH_ASSERTED`, set whenever the latest fix's provenance is Meshtastic `LOC_MANUAL` (translated to a core-side `ff_crew_pos_meta_t.asserted` bool at the shell boundary, `app/ff_shell.c`'s `shell_pos_meta` — core never sees the Meshtastic enum), checked BEFORE any age math so no `now_ms` can move a member off it. `ff_radar_compute` maps this to `RADAR_PLACE`, its own mode — not folded into LIVE/STALE/LOST, mirroring the LOST-vs-NEVER in-kind distinction this spec already draws. `scr_radar.c`'s `radar_render_place`: a solid arrow (a real coordinate exists — an assertion doesn't taint geometry, only age), a neutral "FIXED POSITION" chip (never "LIVE", never a rim tint), and `age_str` is always `""` — issue #33's binding ruling is that `LOC_MANUAL` means "not measured," not "placed deliberately or recently" (hardware showed a six-month-old asserted position under a node heard minutes earlier), so no age is ever honestly renderable for this mode. CLOSE still outranks PLACE by distance or RSSI (proximity is a geometric fact an assertion doesn't taint). Ring dots get the matching `ff_radar_dot_t.place` flag (mutually exclusive with `stale`, drawn as a filled square — a different silhouette, not a differently-styled friend dot); a place mixed into a multi-member CLUSTER marker is a **known gap**, not fixed here (no fixture/golden combines the two yet).
  - **#47 — degraded precision must not render metre-level confidence.** `mc_position_t.precision_bits` (PR #39/#52) reaches the shell; `ff_crew_member_t` now carries `has_precision_bits`/`precision_bits` verbatim. `FF_CREW_POS_PRECISION_MIN_BITS` (21) is the threshold below which a position counts as degraded — derived from this spec's own 30 m close-range predicate (`FF_CREW_CLOSE_RANGE_M`, `core/include/ff_crew.h`): 20 bits grids to ~45.6 m (already coarser than close range), 21 bits to ~22.8 m (comfortably under it, GPS-error scale), so 21 is the lowest bit count still called "precise". When degraded, `ff_radar_view_t.dist_str` becomes an honest AREA estimate (`ff_crew_pos_precision_grid_m`, e.g. `"~5.8 km"`) rather than a fabricated point distance, `dist_imprecise` is set, and the value handed to `ff_crew_close_range`'s distance leg is forced unknown (`-1`) — a coordinate that could be kilometers off cannot honestly support "you are standing next to them"; the RSSI leg is untouched (measured by our own radio, no coordinate dependency). Render treatment (`scr_radar.c`): the distance label dims (INK → MUTED) and the mode chip gets a " - AREA" suffix on LIVE/STALE/PLACE/LOST; CLOSE (reachable here only via the RSSI leg while imprecise) shows "NEARBY" instead of a fabricated big number, since showing the coordinate's own multi-km area text next to pulsing "you are close" rings would directly contradict them. **Absent `has_precision_bits` renders exactly as before this fix, on BOTH the live-packet and want_config-replay ingest paths** — "the sender didn't say" is not evidence of degradation, and treating replay-absent specially (the path that structurally never carries this field, per `mc_client.h`) would regress every ordinary reconnect to a blanket imprecise label; pinned by `test_shell.c`'s `S47_replay_absent_precision_renders_normally_not_degraded`.
  - Fixtures: `radar_place.json` (a landmark, "CAMP BASE"), `radar_imprecise.json` (DANA, LIVE, `dist_imprecise: true`). Every fixture/dump field added by this round (`radar.mode: "place"`, `radar.dist_imprecise`, `radar.dots[].place`) is additive with a `false`/unchanged default, so all 26 pre-existing goldens render byte-identical.
