# S15 · esp32s3 target — the real device (when boards arrive)

## Purpose
Same app, real hardware: ESP-IDF component build for the Waveshare ESP32-S3-Touch-LCD-1.46 UI brain + UART transport to the comms brain.

## Deliverables
1. **ESP-IDF project** under `targets/esp32s3/` (IDF 5.x): components wrap core/meshclient/festpack/app unchanged; `idf.py build flash monitor` works.
2. **Display+touch driver**: SPD2010 QSPI panel + touch via Waveshare's reference code, adapted into an LVGL v9 display/indev driver at 412×412; target ≥25 fps radar.
3. **HAL implementations**: `ff_clock` (esp_timer), `ff_store` (NVS), transport UART (GPIO43/44 ⇒ comms brain D3/D1 = GPIO4/GPIO2 — NOT D6/D7, which Meshtastic gives to the GPS; see docs/hardware/comms-brain.md — 115200, matching Meshtastic Serial Module PROTO mode), QMC5883L driver (I2C) + QMI8658 accel (onboard) feeding `ff_geo_heading_deg`, PWM haptics stub (pin per case design), backlight control.
4. **Power scaffolding v1**: screen-off on 20 s idle, tilt/tap wake via QMI8658 interrupt; light-sleep tuning is post-Lost-Lands (issue).
5. **Bundled assets**: Lost Lands festpack embedded via `EMBED_FILES`.
6. **Comms-brain setup doc** (`docs/comms-brain.md`): flash stock Meshtastic "Seeed XIAO S3", enable Serial Module PROTO on D6/D7, region US, channel setup — with exact CLI commands.
7. CI: `esp32-build` job (build-only) becomes a PR gate.

## Acceptance criteria (bench, manual+scripted)
1. Boots to Radar; goldens visually match sim (photo in PR).
2. mc READY over UART against real comms brain; position from T1000-E rabbit appears ≤10 s.
3. Compass: calibrated heading within ~5° of phone compass at 4 cardinal points.
4. Touch: all S06/S08 interactions work; T9 typing usable.
5. 25+ fps radar; no watchdog resets over 30 min soak.
6. CI esp32 build green.

## Slices
a) IDF skeleton + core compiling · b) display/touch driver · c) UART transport + bench handshake · d) sensors + calibration · e) idle/wake + assets.

## Risks (known, accepted)
SPD2010 LVGL driver is the long pole (Waveshare reference exists but quality varies); UART PROTO mode config has community-reported quirks — fixture-record early on bench. Both were chosen consciously over forking Meshtastic.

- **2026-09-04, `feat/s15c-uart-transport` — slice c landed: deliverable 3's UART transport (GPIO43/44, 115200) + bench handshake.**
  - **New:** `mc_transport_uart.c`/`.h` (`targets/esp32s3/components/ff_meshclient/`) — an `mc_transport_t` over ESP-IDF's `uart` driver, wired into `app_main.c` behind a new `FF_LINK` Kconfig choice (`NONE`, today's default/unchanged behaviour, or `UART`). All pins/port/baud are Kconfig (`FF_UART_PORT`, `FF_UART_TXD`/`FF_UART_RXD` default 43/44 per deliverable 3 and `docs/hardware/comms-brain.md`'s pin map, `FF_UART_BAUD` default 115200) — a header remap needs no code change.
  - **Port choice: UART1, not UART0 — hardware-verified, not assumed.** GPIO43/44 are ALSO UART0's own default TX/RX pins, so the obvious first guess is UART0. It is wrong for this target: the maintainer's real board `sdkconfig` (read directly, not inferred) has `CONFIG_ESP_CONSOLE_UART_DEFAULT=y`, `CONFIG_ESP_CONSOLE_UART=y`, `CONFIG_ESP_CONSOLE_UART_NUM=0` — UART0 is the PRIMARY log console today, with `CONFIG_ESP_CONSOLE_SECONDARY_USB_SERIAL_JTAG=y` only as the secondary mirror (confirmed against `esp-idf`'s own `components/esp_system/Kconfig` `ESP_CONSOLE_UART`/`ESP_CONSOLE_SECONDARY` choices: this is ESP-IDF's stock default combo for this target, not a project override, and `app_main.c`'s pre-existing S26f comment already said as much — "USB-Serial/JTAG is the SECONDARY console"). `esp_console` already owns `uart_driver_install()` on UART0 in that configuration; installing this transport's own driver on the same port would either fail (`ESP_ERR_INVALID_STATE`) or interleave framed protobuf bytes with plain-text log lines on the same wire. UART1 has no such conflict — ESP32-S3's UART peripherals route through the GPIO matrix, so remapping UART1 onto GPIO43/44 via `uart_set_pin()` costs nothing and needs no console reconfiguration. `FF_UART_PORT_0` stays offered in Kconfig for a future maintainer who deliberately moves the console to USB-Serial/JTAG only — this slice does not make that change.
  - **`write()` honours the #170 `mc_transport_t` contract — the actual bug ESP-IDF's own docs paper over.** `uart_write_bytes()` with a TX ring buffer enabled (required here for the ≥1 KB ring the spec asks for) calls FreeRTOS's `xRingbufferSend()` with `portMAX_DELAY` for whatever doesn't currently fit (verified against `esp-idf/components/esp_driver_uart/src/uart.c`'s `uart_tx_all()`) — i.e. it BLOCKS the calling task on a full ring rather than returning early, which is exactly the reconnect-storm/UI-stall failure mode the #170 amendment (`docs/specs/S03-meshclient.md`) exists to prevent. Fix: query `uart_get_tx_buffer_free_size()` first and never ask `uart_write_bytes()` for more than a call already knows fits (minus a small margin for `uart_tx_all()`'s own internal ring-buffer header item) — so the call actually made is known in advance not to block. `read()` is a direct 1:1 mapping onto `uart_read_bytes(..., 0)` (0 ticks = nonblocking): `>0` bytes, `0` = nothing available (not an error), `-1` = hard failure. The accept-length arithmetic is pulled into `mc_transport_uart_accept.h` (zero ESP-IDF includes) specifically so it has a real, host-run Unity test (`test_transport_uart_accept.c`) even though the transport itself is device-only — see "Tests" below.
  - **Loopback self-test, `CONFIG_FF_UART_LOOPBACK_SELFTEST` (default `n`).** Bench aid for proving the driver + header pins before the comms brain exists: jumper the header's TXD pin directly to its RXD pin, enable the option, flash. At boot, `app_main.c` writes a known 64-byte pattern (`0x00`..`0x3F`) through the transport's own `read()`/`write()` callbacks (not raw `uart_*` calls — a PASS proves the exact `mc_transport_t` the shell will run on) and reads it back within 100 ms, logging `S15c UART loopback self-test: PASS` or `FAIL` with byte counts either way. Documented in `docs/hardware/comms-brain.md`'s "Bring-up order" step 1 (landed slightly ahead of this PR, #196/#197 — same Kconfig name, confirmed no drift).
  - **Bench handshake — what to expect, and what a wiring/config mistake looks like.** Boot log sequence once `FF_LINK_UART` is selected and a comms brain is wired per `docs/hardware/comms-brain.md`:
    1. `link: UART1 TXD=43 RXD=44 115200 -> Meshtastic PROTO` — printed once at boot, success or failure (a driver-install failure logs `OPEN FAILED (<esp_err_t>)` instead and falls back to `cfg.transport` zeroed, i.e. today's exact no-link behaviour — see `ff_link_uart_setup()`, `app_main.c`).
    2. `S15c link state: NONE (no transport, or never connected) -> RECONNECTING (handshake in flight, or retrying after a drop)` — `ff_shell_init` saw a live transport and called `mc_connect()` immediately.
    3. `S15c link state: RECONNECTING (...) -> CONNECTED (want_config complete, mc_client READY)` — expected within a few seconds against a comms brain already running Meshtastic's Serial module in PROTO mode (AC2's "mc READY ... within N s"; comms-brain.md step 4 puts this within "a few seconds").
    - **Wrong-crossed TX/RX** (puck TXD not actually reaching the comms brain's RXD, or vice versa): **silence** — the link state never leaves `RECONNECTING`, `mc_get_stats()`'s `frames_ok`/`frames_resynced` stay at 0 forever (nothing to resync — no bytes ever arrive to be framed at all), and `mc_client`'s 30 s-silence reconnect timer fires repeatedly with nothing to show for it. No framing garbage, because no bytes are received at all.
    - **Wrong baud** (either side's `FF_UART_BAUD`/`serial.baud` mismatched): the opposite symptom — **framing garbage**, not silence. Bytes DO arrive (the wire is live), but sampled at the wrong bit period they never line up with the `0x94 0xC3 [len_hi] [len_lo]` magic (`docs/specs/S03-meshclient.md`'s framing section); `mc_get_stats().frames_resynced` climbs continuously as `mc_framer_t` scans for a magic sequence it never finds, and `frames_ok` stays at 0. This is the one case the loopback self-test above cannot catch on its own (it always talks to itself at its own configured baud, so it can never disagree with itself) — it is a live-comms-brain-only failure mode, called out here rather than silently assumed caught.
  - **Sender wiring — simpler than the brief anticipated.** `ff_shell_init` (`app/include/ff_shell.h`) already binds the outbound `ff_wiring_sender_t` to the SAME live `mc_client_t` by default whenever `cfg->transport` has a live `read`/`write` pair — no `ff_shell_set_sender()` override is needed on this path (that call exists for the demo build's loopback sender specifically because it has no transport to default to). `app_main.c` therefore only sets `cfg.transport` before `ff_shell_init`, mirroring how the sim's `live_setup.c` sets `shell_cfg->transport` before its own `ff_shell_init` call.
  - **Tests — the honest gap.** The transport itself (`mc_transport_uart.c`) is device-only: it `#include`s ESP-IDF's `<driver/uart.h>` and calls `uart_driver_install()`/`uart_get_tx_buffer_free_size()`/`uart_read_bytes()`/`uart_write_bytes()`, none of which exist off-device, so there is no host build for it and no ctest exercises the real driver interaction (ring-full backpressure, actual byte transfer) — only the bench self-test and a live comms brain can.
