# S10 · flare flow

## Purpose
The loudest signal: send/receive come-find-me. Mockups "Radar — close range" (send button) and "Flare — takeover" (receive) are layout authority.

## Behavior
- **Send:** FLARE button (close-range face) or Crew row long-press → confirm sheet ("FLARE to crew?") → `ff_proto_encode_flare(dur=300)` broadcast with want_ack; sender UI enters "FLARING" state (own screen pulses amber, status line "you are flaring — crew arrows locked on you"), cancel button sends FLARE_END. Auto-end at dur.
- **Receive (paired sender only):** full-screen takeover regardless of current face; haptic pattern (3 long) **overrides quiet hours**; GO → radar with sender force-selected + flare-lock (selection cycling disabled until flare ends/dismissed); DISMISS → back, feed item remains. Takeover expires at dur or FLARE_END.
- Multiple flares: newest wins the takeover; feed keeps all.
- State machine in core (`ff_flare.h`): IDLE/SENDING/RECEIVED(node,expiry)/LOCKED; transitions pure, tested; app renders.

## Acceptance criteria
1. State table: 12 transition tests incl. expiry, FLARE_END, newest-wins, unpaired-sender-ignored.
2. Receive during quiet hours still fires haptic callback (flag asserted in mock).
3. GO locks selection: `ff_crew_select_next` no-ops while LOCKED; unlock on expiry restores cycling.
4. Sender auto-end at dur: clock-advance test emits FLARE_END exactly once.
5. Goldens: `flare_takeover.json`, `radar_flare_locked.json` (radar with lock chip), `flaring_self.json`.

## Slices
a) state machine + tests · b) takeover + sender UI + goldens (needs S06 shell).

## Amendments
- **2026-08-23, PR #15:** Independent review of slice (a) flagged that the original `ff_flare.h` shape — one shared "current flare" slot for IDLE/SENDING/RECEIVED(node,expiry)/LOCKED — conflated two, and in one case three, genuinely independent facts. Two rulings, both implemented in PR #15:
  - **Ruling 1 (HIGH — outbound send and inbound receive are independent):** if a paired crew member's flare arrives while I am mid-send, the single-slot design silently overwrote my `SENDING` state with the incoming `RECEIVED`, with no `FLARE_END` emitted for my own flare — `ff_flare_send_cancel()` then permanently no-op'd (state was no longer `SENDING`) for the rest of my flare's duration, with zero recourse. Ruling: "I am sending a flare" and "I am receiving someone's flare" are separate, concurrent state — they are legitimately both true at once in the field (I flare for help; a crew member flares back or independently 20s later; neither is stale or wrong). `ff_flare_t` now tracks `sending`/`send_expiry_ms` as a field group that nothing inbound ever reads or writes; `ff_flare_send_cancel()` works regardless of any incoming flare, and each of the two timers (my send, the incoming takeover) expires independently in `ff_flare_tick`.
  - **Ruling 2 (MEDIUM — an established LOCK is never silently replaced):** the spec's "newest wins the takeover" line is genuinely ambiguous about whether an already-`GO`'d LOCKED selection is "the takeover" a newer flare can win away, or a stickier commitment the user already made. Ruling: a newer paired flare MAY still raise its own full-screen takeover (the urgency framing is real — the crew member needs to be seen) but does NOT touch an existing lock. If I've pressed GO and am walking toward Dana (LOCKED to her), and Kev flares, I see Kev's takeover while my selection stays locked on Dana underneath; DISMISS on Kev's takeover returns me to the intact Dana lock; GO on Kev's takeover is the explicit decision that switches the lock to Kev. Rationale: silently changing where the arrow points mid-walk without an explicit choice is exactly the "confident but wrong arrow" failure this product exists to prevent (CLAUDE.md: "honest data over pretty data" — the currently-locked node must always be a fact the user chose, not one the network chose for them). `ff_flare_t` now tracks the pending takeover (`takeover_active`/`takeover_node_id`/`takeover_expiry_ms`) and the lock (`locked_node_id`/`locked_expiry_ms`) as separate fields; only `ff_flare_go()` writes `locked_node_id`, cleared only by `ff_flare_release_lock()`/its own expiry/a matching FLARE_END (see the third entry below for why that's `ff_flare_release_lock()` and not a `ff_flare_dismiss()`).

  Acceptance criterion 1's "IDLE/SENDING/RECEIVED(node,expiry)/LOCKED" state-table language above predates this amendment; see `ff_flare.h`'s doc comment for the current three-independent-fields shape (`sending`, `takeover_active`+node+expiry, `locked_node_id`+expiry) that replaces it, and `test_flare.c`'s `S10_ruling1_*`/`S10_ruling2_*` tests for the regression coverage.

- **2026-08-23, PR #15 (third entry — same PR, follow-up review round):** the PR was approved with one non-blocking recommendation, which was taken immediately (same slice) rather than deferred: **Ruling 3 — split the single, mode-dependent `ff_flare_dismiss()` into two explicit, intent-aware functions**, `ff_flare_dismiss_takeover()` (clears a pending takeover only, no effect on the lock) and `ff_flare_release_lock()` (releases the navigation lock only, no effect on a pending takeover). Reviewer's concrete repro: with double-duty `dismiss()`, a user tapping "stop navigating" at the exact instant a new flare's takeover arrives silently gets routed into the takeover-dismiss branch — the user's actual intent (release the lock) is dropped, *and* the new takeover is swallowed unseen (never shown, never decided). A mode-dependent API can't distinguish those two intents; only the caller knows which one it meant. Rationale for taking this now rather than deferring: nothing in this repo calls `ff_flare_dismiss()` yet (slice b/UI wiring hasn't started), so this is a pure addition-then-removal with zero call sites to update — done after slice b existed, this would have been a breaking `[api]` change against real call sites instead. `test_flare.c`'s `S10_ruling3_*` tests cover both split functions' independence, including the reviewer's exact race case (`S10_ruling3_release_lock_while_takeover_pending_keeps_takeover_visible`: takeover pending + `ff_flare_release_lock()` called → lock released, takeover still pending and still visible).

- **2026-08-23, issue #27 / PR #41 (takeover disclosure chip — wording, not substance).**

  **Provenance first, because the first draft of this entry got it wrong.** The requirement that the takeover screen disclose what pressing GO costs comes from **PR #20's UX review, BLOCKING finding #3 — "GO must disclose what it costs"** — the source `ff_flare_fmt_go_switches_lock`'s doc comment already cites. It does **not** come from Ruling 2 above, which is entirely state-machine semantics: that a newer flare never touches an existing lock, that DISMISS returns to the intact lock, that GO is the explicit decision that switches it, and that the locked node must be a fact the user chose. Ruling 2 is why an established lock is the user's decision to make; finding #3 is why the screen has to say what that decision costs. PR #41's code review caught this amendment (and `flare_fmt.h`) attributing the second to the first. Corrected here, because the whole purpose of writing the requirement down is that a future re-wording can be checked against it — and a citation pointing at a paragraph that does not contain the requirement is worse than no citation at all.

  **What shipped.** The chip is `GO DROPS LOCK - DANA` at 20px (`ff_flare_fmt_lock_cost`, `app/screens/flare_fmt.h`). It replaces PR #20's `LOCKED ON DANA - GO SWITCHES TO KEV` (36 characters, two clauses, 14px chip type) — legible and correct, but a *read* rather than a *glance* on the one screen that interrupts the user mid-panic at 2 AM, which is what issue #27 was opened to fix.

  **The route there is worth recording, because the obvious short form was wrong.** PR #41's first pass shortened it to `GO: DANA → KEV`, which carried every fact but failed in a way that is easy to reproduce and hard to see from a desk: shortening had deleted the sentence's **verb**, and the verb was the disclosure. `A → B` means *via* or *then* in every context a person meets it outside this app — breadcrumbs, file paths, map directions — so the chip read as an itinerary ("go to Dana, then Kev"), i.e. as **keeping** the lock. It also deleted the word **LOCK**, which is the only vocabulary the user has for this concept: the Radar face's own chip reads `LOCKED - DANA`, and the takeover screen had stopped connecting to it. Constraints for any future re-wording, in order:
  1. **A verb of loss is mandatory.** A glyph, an arrow, a colon or any other punctuation cannot carry "instead of" — those all read as sequence.
  2. **The word LOCK (or LOCKED) stays**, and the ` - <name>` tail matches the Radar face's lock chip, so the two chips visibly belong to each other.
  3. **The incoming sender is deliberately NOT on the chip.** It is the takeover's 22px headline directly above, built unconditionally by the same function that builds the chip. Naming them twice spends the chip's entire width budget on the largest thing already in view. This split is only honest while the headline exists, so it is pinned by `S10_ACn_lock_disclosure_is_always_accompanied_by_the_headline` rather than left as a convention.

  **Name truncation is a PIXEL bound, not a character count, and this is the second thing this entry has had to correct.** PR #41's first pass capped the locked name at 11 bytes with an explicit `...`. That was wrong in a way that looked right: Montserrat is proportional, so a byte count constrains rendered width only if every glyph is the same width. The code review measured eleven `W`s at 487px against a 440px circle — 25px past the bezel — while eleven typical characters fit with room to spare. Crew names are Meshtastic `User.long_name`: arbitrary UTF-8 chosen by someone else and arriving over the radio, so this was reachable from untrusted input, and it is the same class of bug as PR #25's off-glass back button. The guard's own test asserted it could not happen, using names that were a *length* worst case and not a *width* one — a guard whose test passes for the wrong reason is worse than no guard.

  So the constraint is now expressed in the units it is actually measured in. `ff_flare_fmt_lock_cost` does **not** truncate at all; it emits the name whole. `scr_flare.c`'s chip builder clamps the label to `ff_layout_centered_band_max_width()` — the `ff_layout.h` primitive that exists, in its own words, so a layout is "sized to fit the glass **by construction**, rather than built rectangle-first and only checked ... after the fact" — and lets LVGL's `LV_LABEL_LONG_MODE_DOTS` place the ellipsis at the correct pixel. Two consequences worth recording: a name of narrow glyphs is no longer cut for no reason (the byte cap truncated `IIIIIIIIIIIIIII` and `WWWWWWWWWWWWWWW` identically, though the first fits with 62px to spare), and no future adjustment of a character count can silently move the chip off-glass, because no character count is consulted. **Any future re-working of this chip must keep the bound in pixels.** The guarantee is enforced by `S10_ACn_lock_disclosure_chip_stays_inside_the_round_glass`, which now sweeps width worst cases (`WWWWWWWWWWWWWWW`, `MMMMMMMMMMMMMMM`, `MWMWMWMWMWMWMWM`, …) rather than one length worst case, and by `S10_ACn_lock_disclosure_only_truncates_names_that_dont_fit`, which pins the other half — a name that FITS must not be cut. Deliberately **not** by a golden: CI proved that LVGL's `LV_LABEL_LONG_MODE_DOTS` places its ellipsis on a different character on x86-64 Linux than on arm64 macOS (2.27% of pixels, against 0.0000% for every other fixture), so a truncated chip cannot be the subject of a byte comparison. The rendered proof is `docs/screens/flare-takeover-wide-name.png`; see `firmware/tests/fixtures/README.md` for the full note.

  One detail that is easy to get wrong when clamping: LVGL's dots mode triggers on **vertical** overflow, so a width-only clamp makes the text wrap to a second line and grow the chip taller instead of producing an ellipsis. The label's height must be pinned to one line for the clamp to do what it looks like it does.

  **One glyph note that is now historical but worth keeping**, because the constraint it checked is real and will come up again: `→` (U+2192) is *not* in the compiled Montserrat subset (text range `0x20-0x7F`, `0xB0`, `0x2022` — the same gap that forced U+00B7 MIDDLE DOT into a hyphen across this codebase), but LVGL's built-in FontAwesome range *is* compiled in, and `LV_SYMBOL_RIGHT` (61524 / `0xF054`) is present in every Montserrat size this repo enables — verified at the compiled-font level, not from the generator comment. The glyph rendered correctly. It was still the wrong design, which is the lesson: coverage was answerable and answering it did not make the arrow mean "instead of". The shipped wording uses no symbol glyph at all.

- **2026-09-02, fix/flare-lock-selects-sender.** Independent review (with a scratch test) found that AC3's "GO locks selection" was true of the flare LOCK (`ff_flare_t.locked_node_id`) but not of the radar-face SELECTION `ff_radar_compute` actually renders (`ff_crew_t.selected_slot` via `ff_crew_selected()`): with 3+ paired crew members, GO on a flare from anyone other than the first-paired/self-healed selection left the radar arrow pointing at the PREVIOUS selection, not the sender — "come find me" pointed at the wrong person. `ff_flare_go()` had never been wired to touch crew selection at all; it only ever wrote the lock, by design (see `ff_flare.h`'s "Dependency-light by design" section — `ff_flare` deliberately has no `ff_crew.h` dependency).

  **Mechanism chosen: (b), "GO force-selects."** A new core function, `ff_crew_select_node(ff_crew_t *c, uint32_t node_id)` (`core/include/ff_crew.h`), forces the radar-face selection directly to a given paired node id (no-op if that id isn't a paired member — same rule `ff_crew_selected`'s self-heal already enforces). The app shell's `FF_INTENT_TAKEOVER_GO` handler (`ff_shell.c`) now calls it immediately after `ff_flare_go()`, passing `ff_flare_locked_node(&sh->flare)` — the value the lock itself just committed to, so the selection can never drift from what the lock chip on Radar already says.

  The alternative, (a) "radar follows the lock" (teaching `ff_radar_compute` to target the lock instead of/ahead of `ff_crew_selected()`), was rejected here: it would require a new parameter on `ff_radar_compute`'s signature, touching that function's ~35 existing call sites in `core/tests/test_radar.c` alone, for no behavioral difference from (b) in the cases this bug covers — `ff_flare_go`/`ff_crew_select_node` already run back-to-back at the one real call site, so there is no window where the lock and the selection can be observed to disagree. (a) remains the better choice on a hypothetical future face that reads `ff_crew_selected()` independently of the lock and needs to *automatically* revert when the lock releases; no such face exists yet, so this fix does not preempt it.

  **Expiry rule (mechanism (b)'s own):** the lock's own expiry (`ff_flare_tick` clearing `locked_node_id`, or a matching `FLARE_END`) does **not** revert the radar selection to whoever was selected before GO. The user is left looking at the sender and can re-select someone else explicitly (`ff_crew_select_next`) if they want to — this is a deliberate asymmetry with mechanism (a), where "the radar follows the lock" would imply reverting automatically once the lock is gone. Chosen because GO is stated (AC3, Ruling 2/3) as the user's own explicit navigation decision, not a transient highlight tied to the lock's lifetime — nothing in the spec says the selection itself is supposed to un-commit when the countdown runs out, only that *cycling* (`ff_crew_select_next`) is unlocked again.

  DISMISS (`ff_flare_dismiss_takeover`) is untouched by this fix and was already correct: it never called anything selection-related, so the radar target was already unaffected by a dismissed takeover.

  Tests: `core/tests/test_crew.c`'s `S10_select_node_*` (the new function, direct); `app/tests/test_intent.c`'s `S10_notif_flare_go_force_selects_the_sender_not_the_prior_selection` (the actual regression — DANA pairs first/self-heals by default, KEV flares, GO must land on KEV, from all nine starting states), `S10_notif_flare_dismiss_does_not_change_the_radar_selection`, and `S10_notif_flare_lock_expiry_leaves_selection_on_the_sender` (the expiry rule above). Mutation-checked: reverting the `ff_crew_select_node(...)` call in `ff_shell.c`'s `FF_INTENT_TAKEOVER_GO` handler makes `S10_notif_flare_go_force_selects_the_sender_not_the_prior_selection` fail at the very first starting state (`Expected 'KEV' Was 'DANA'`), confirmed against a freshly rebuilt (not stale) binary.

  Golden `radar_flare_locked.json` is unaffected: it is a hand-authored fixture consumed directly by `firmware/targets/sim/fixture_view.c`'s renderer (`radar.name` and `flare.locked_from_name` are independent JSON fields the fixture sets to agree, "DANA" both), never derived from `ff_shell`'s actual crew/flare wiring — so it never depended on the selection bug this fix addresses, and stays byte-identical. No new golden was added.

No test needed beyond the existing `radar_layout_resolve_dots` sweep.
  - The compass ARROW is a real conflict: for bearings within roughly `±25-31°` of due north its shaft runs straight up through the chip's own x=0 center, unshortened (nothing in the STATUS_BAR/PAGE_DOT registry stops it, and the chip itself is deliberately not registered — see `scr_flare.h`'s doc comment). This can't be designed away by tuning the DY (shrinking the gap only narrows the cone; moving the chip down widens it), so the fix accepts it: the chip may paint OVER the arrow for that narrow cone, which `scr_nav.c` already does in z-order (`ff_scr_flare_build_lock_chip` is called AFTER `ff_scr_radar_build`) — only painting over the STATUS BAR was ever the bug.   - `RADAR_CLOSE` mode's own pulsing-ring registry rect grazes the chip's y-band at its outermost (faintest) ring only — not exercised by any fixture today, flagged rather than solved in `radar_layout.h`'s comment, alongside that file's pre-existing note that these radar-chrome DYs are hardcoded (not radius-relative) offsets awaiting a systemic tidy.

- **2026-09-03, fix/radar-lock-chip-clears-status-bar (coordinator follow-up, `[api]`).** Independent verification of the fix above rendered a due-north locked fixture (`arrow_deg` 0, `ring_deg` 0) that the original golden never covered, and found the compass arrow's HEAD painted squarely under the lock chip.   **Derivation** (`radar_layout.h`'s own comment on the constant has the full working): the chip's own bottom edge is `RADAR_LAYOUT_LOCK_CHIP_DY + 14.0f` (the chip's half-height) `= -108`. So bounding bearing 0 alone bounds every bearing. Requiring an `>=8px` clearance from the chip's bottom edge, plus the same 16px ("double the floor") margin convention the chip's own DY used against the status bar:

  ```
  max reach = -(chip bottom edge) - gap = 108 - 16 = 92
  ```

Concretely — `mc_client.c`'s inbound decode switch (`mc_process_mesh_packet`) recognizes exactly three portnum classes (`TEXT_MESSAGE_APP`, `POSITION_APP`, the `FF_PORTNUM`-range PRIVATE payloads); any other portnum, including Meshtastic's `ROUTING_APP` (the portnum an implicit ack/nak reply arrives on), falls through to the `else` branch and is silently counted in `c->stats.decode_skipped` — never decoded, never delivered to any `mc_events_t` callback. So there is no ack/nak event for the app layer to observe, at any layer, today. A future `FF_FLARE_WIRE_ACKED` (or similar) state is real future work, not implemented here, and would need: (1) `mc_client.c` to decode `ROUTING_APP` packets (a `meshtastic_Routing` body, correlated to the original send via `MeshPacket.id`/the routing reply's `request_id` field — neither currently read anywhere in this library) and (2) a new `mc_events_t` callback (e.g. `on_routing_ack(void *u, uint32_t request_id, bool ok)`) to deliver it, which `ff_shell.c` would then wire into `ff_flare_wire_mark_attempt` or a new sibling. Both are meshclient-layer additions outside this PR's `app/ff_shell.c`+`app/ff_wiring.*` scope.

  **Tests.** `firmware/meshclient/tests/test_meshclient.c`: `S03_want_ack_mc_send_private_true_sets_meshpacket_want_ack` / `_false_leaves_meshpacket_want_ack_unset` — pins that `mc_send_private`'s `want_ack` bool already reached the encoded `MeshPacket.want_ack` field before this PR (nanopb-decodes the captured ToRadio bytes; this was previously untested at the wire level even though the parameter existed). `app/tests/test_shell.c`: `S10_wire_flare_start_sets_want_ack`, `S10_wire_cancel_after_sent_does_not_set_want_ack`, `S10_want_ack_inbox_flare_to_scope_sets_want_ack` (see above).

- **2026-09-04, fix/flare-cancel-taps — the sender overlay never rebuilds for its own countdown; CANCEL's dim absorbs taps; the device rebuild/touch race closed.** Maintainer report, on glass, after a 5x HOME quick flare: "the CANCEL button doesn't work well — taps seem to pass through and I tapped it multiple times before it actually worked." Three independent root causes, all confirmed (one by static reading, one by a failing test, one by code reading + the documented esp_lvgl_port contract — no sim repro possible, see below), all fixed in this one PR; a fourth suspected cause (CANCEL covered by a later-built sibling / the scroll-catcher idiom) was checked and does NOT reproduce.

  **Root cause (a) — the countdown dirtied the render key once a second for a flare's whole life.** `shell_render_key` (`app/ff_shell.c`) used to coarsen `flare.send_expires_in_ms` to whole seconds via `shell_coarsen_ms` and leave it IN the key — the same "coarsen to what the screen actually renders" discipline the file correctly uses for ages and the radar arrow elsewhere, but wrong here: unlike those, a live countdown's coarsened value changes on EVERY tick that crosses a 1s boundary, i.e. once a second for up to 300s. A dirty key gets a full `lv_obj_clean()` + rebuild (`app_main.c` / `sim_lifecycle.c`), which tears down and recreates the sender overlay's own CANCEL button once a second. A CANCEL press/release straddling one of those rebuilds has its pressed object deleted out from under it, so LVGL never fires the CLICKED — the on-glass symptom exactly. Auditing the two SIBLING countdown fields the same way found they were pure key-pollution with no display consumer at all: `takeover_expires_in_ms` and `locked_expires_in_ms` are projected and coarsened into the key but never read by `ff_scr_flare_build_takeover`/`ff_scr_flare_build_lock_chip`/anywhere else that renders a pixel (grepped) — so both are now excluded from the key too, removing an identical (if less visible — no CANCEL-equivalent sits under them) once-a-second churn source on the takeover screen and on Radar while locked.

  **The fix.** All three fields are now excluded from the render key (`key->flare.*_expires_in_ms = 0`, the same "#bug1" shape `brightness_pct` already established for a live value with no key-safe way to represent "just keep rendering the latest one"). `send_expires_in_ms` still needs to reach the glass — it does so through a NEW path entirely outside the dirty/rebuild mechanism: `ff_scr_flare_build_sender_overlay` (`app/screens/scr_flare.c`) stashes a pointer to the countdown chip's label (armed with a self-nulling `LV_EVENT_DELETE` callback, so the pointer can never go stale across an unrelated rebuild) and a new `ff_scr_flare_sender_overlay_tick(int32_t send_expires_in_ms)` (`[api]`, `scr_flare.h`) updates that ONE label's text in place. A shared `ff_face_dispatch_tick(state)` (`[api]`, `app/ff_face_dispatch.h`) forwards to it while `state->flare.sending`; both `app_main.c` and `targets/sim/sim_lifecycle.c` (the one place `ctl_loop.c`/`main.c`/`ff_demo_run.c` all funnel per debt/sim-window-lifecycle) call it every frame, independent of `rebuild_pending`/dirty — the exact "outside the render key" placement those files already use for live brightness/screen_flip. `takeover_expires_in_ms`/`locked_expires_in_ms` need no such replacement — nothing renders them.

  **Root cause (b) — the dimmed base face was never actually made un-clickable, only dimmed.** `scr_nav.c` and `scr_launcher.c` both dim their base content to `LV_OPA_30` while `flare.sending` (PR #20's own fix for "flaring_self reads as an error") and separately clear `LV_OBJ_FLAG_CLICKABLE` on the `content` wrapper itself — but LVGL's hit search (`lv_indev_search_obj`, vendored `lvgl/src/indev/lv_indev.c`) recurses into a container's CHILDREN regardless of the CONTAINER's own clickable flag, falling back to consulting the container's flag only once none of its descendants match. So a tap anywhere on the dimmed face still reached whatever real, still-clickable control sat under it — a launcher satellite, an inbox row, a settings toggle — even though visually the screen read as "grayed out, this is the CANCEL screen now." Fixed by adding a genuinely CLICKABLE, full-puck "dim catcher" (`ff_scr_flare_build_sender_overlay`, built after the caller's `content` and before this overlay's own CANCEL) with no event callback of its own: LVGL's front-to-back search finds CANCEL first for a tap that lands on it, and finds the catcher first for every other tap on the puck, absorbing it before the search ever reaches `content`'s subtree. Transparent (`LV_OPA_TRANSP`) — changes what a tap DOES, never what the screen LOOKS like (goldens unaffected).

  **Root cause (c) — the device's finger-down check and the rebuild it gates were not atomic.** `app_main.c` used to read `!ff_display_touch_is_down()` OUTSIDE the `ff_display_lock()` the rebuild takes a few lines later. `ff_display_lock`/`_unlock` are bare aliases for esp_lvgl_port's own `lvgl_port_lock`/`_unlock` (`ff_display.c`'s "LVGL task lock" section) — the exact mutex esp_lvgl_port's own task holds for the ENTIRE duration of every `lv_timer_handler()` call it makes, which is where the touch read callback (`ff_touch_gate_read_cb`) actually runs (LVGL's indev read timer fires from inside `lv_timer_handler`). So a window existed: this task reads "no finger down" as true, then — before it reaches `ff_display_lock()` — the port task runs a `lv_timer_handler()` pass that processes a NEW physical press (setting `s_touch_raw_down` true, delivering PRESSED into LVGL), and this task then takes the lock and rebuilds anyway, destroying the button that had just gone pressed. Fixed by taking the lock FIRST and re-checking `touch_is_down()` (and doing the whole clean+rebuild) WHILE STILL HOLDING it, making the check and the port task's own touch processing mutually exclusive. Not reproducible in the single-threaded sim (`ctl_loop.c`/`sim_lifecycle.c` read `ctx->pointer_state` directly with no cross-task handoff at all — `sim_lifecycle.h`'s own doc comment already states the finger-down term is "the RAW pointer-down truth"), so this fix is verified by code reading against esp_lvgl_port's documented lock contract and a zero-warning ESP-IDF device build, not by an automated test.

  **A fourth, related bug found empirically while writing the straddle test for (a), not anticipated by the task brief: `ff_shell_keep_awake` did not include `flare.sending`.** A send left untouched past `FF_IDLE_T_DIM_MS` (15s — trivial inside a 300s send) let the idle FSM dim the screen out from under it; S26(c)'s own wake-only-touch amendment then swallows the NEXT tap on CANCEL entirely (it only wakes the screen, never reaches the button), needing a SECOND, separate tap to actually cancel — independent of (a)/(b)/(c) and, on its own, sufficient to reproduce the maintainer's exact "I tapped it multiple times before it actually worked" report. Fixed the same way `takeover_active`/`quick_flare_pending` already do: `view->flare.sending` is now a fifth keep-awake source (`ff_shell_keep_awake`, `app/ff_shell.c`/`.h`) — a send's own undo button must stay reachable with a single tap for the send's whole life, exactly like a pending takeover's GO/DISMISS already do.

  **Checked and does NOT reproduce — CANCEL covered by a later sibling / the scroll-catcher idiom.** `ff_scr_pill_create` (which `flare_make_button` uses for CANCEL) already routes through `ff_scr_button_create`, which clears `LV_OBJ_FLAG_PRESS_LOCK` for every button in the tree (#145/#148) — CANCEL gets this for free, no separate fix needed.
