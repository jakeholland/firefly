# S10 · flare flow

## Purpose
The loudest signal: send/receive come-find-me. Mockups "Radar — close range" (send button) and "Flare — takeover" (receive) are layout authority.

## Behavior
- **Send:** FLARE button (close-range face) or Crew row long-press → confirm sheet ("FLARE to crew?") → `ff_proto_encode_flare(dur=300)` broadcast with want_ack; sender UI enters "FLARING" state (own screen pulses amber, status line "you are flaring — crew arrows locked on you"), cancel button sends FLARE_END. Auto-end at dur.
- **Receive (paired sender only):** full-screen takeover regardless of current face; haptic pattern (3 long) **overrides quiet hours**; GO → radar with sender force-selected + flare-lock (selection cycling disabled until flare ends/dismissed); DISMISS → back, feed item remains. Takeover expires at dur or FLARE_END.
- Multiple flares: newest wins the takeover; feed keeps all.
- State machine in core (`ff_flare.h`): IDLE/SENDING/RECEIVED(node,expiry)/LOCKED; transitions pure, tested; app renders.

## Acceptance criteria
1. State table: 12 transition tests incl. expiry, FLARE_END, newest-wins, unpaired-sender-ignored.
2. Receive during quiet hours still fires haptic callback (flag asserted in mock).
3. GO locks selection: `ff_crew_select_next` no-ops while LOCKED; unlock on expiry restores cycling.
4. Sender auto-end at dur: clock-advance test emits FLARE_END exactly once.
5. Goldens: `flare_takeover.json`, `radar_flare_locked.json` (radar with lock chip), `flaring_self.json`.

## Slices
a) state machine + tests · b) takeover + sender UI + goldens (needs S06 shell).

## Amendments
- **2026-08-23, PR #15:** Independent review of slice (a) flagged that the original `ff_flare.h` shape — one shared "current flare" slot for IDLE/SENDING/RECEIVED(node,expiry)/LOCKED — conflated two, and in one case three, genuinely independent facts. Two rulings, both implemented in PR #15:
  - **Ruling 1 (HIGH — outbound send and inbound receive are independent):** if a paired crew member's flare arrives while I am mid-send, the single-slot design silently overwrote my `SENDING` state with the incoming `RECEIVED`, with no `FLARE_END` emitted for my own flare — `ff_flare_send_cancel()` then permanently no-op'd (state was no longer `SENDING`) for the rest of my flare's duration, with zero recourse. Ruling: "I am sending a flare" and "I am receiving someone's flare" are separate, concurrent state — they are legitimately both true at once in the field (I flare for help; a crew member flares back or independently 20s later; neither is stale or wrong). `ff_flare_t` now tracks `sending`/`send_expiry_ms` as a field group that nothing inbound ever reads or writes; `ff_flare_send_cancel()` works regardless of any incoming flare, and each of the two timers (my send, the incoming takeover) expires independently in `ff_flare_tick`.
  - **Ruling 2 (MEDIUM — an established LOCK is never silently replaced):** the spec's "newest wins the takeover" line is genuinely ambiguous about whether an already-`GO`'d LOCKED selection is "the takeover" a newer flare can win away, or a stickier commitment the user already made. Ruling: a newer paired flare MAY still raise its own full-screen takeover (the urgency framing is real — the crew member needs to be seen) but does NOT touch an existing lock. If I've pressed GO and am walking toward Dana (LOCKED to her), and Kev flares, I see Kev's takeover while my selection stays locked on Dana underneath; DISMISS on Kev's takeover returns me to the intact Dana lock; GO on Kev's takeover is the explicit decision that switches the lock to Kev. Rationale: silently changing where the arrow points mid-walk without an explicit choice is exactly the "confident but wrong arrow" failure this product exists to prevent (CLAUDE.md: "honest data over pretty data" — the currently-locked node must always be a fact the user chose, not one the network chose for them). `ff_flare_t` now tracks the pending takeover (`takeover_active`/`takeover_node_id`/`takeover_expiry_ms`) and the lock (`locked_node_id`/`locked_expiry_ms`) as separate fields; only `ff_flare_go()` writes `locked_node_id`, cleared only by `ff_flare_release_lock()`/its own expiry/a matching FLARE_END (see the third entry below for why that's `ff_flare_release_lock()` and not a `ff_flare_dismiss()`).

  Acceptance criterion 1's "IDLE/SENDING/RECEIVED(node,expiry)/LOCKED" state-table language above predates this amendment; see `ff_flare.h`'s doc comment for the current three-independent-fields shape (`sending`, `takeover_active`+node+expiry, `locked_node_id`+expiry) that replaces it, and `test_flare.c`'s `S10_ruling1_*`/`S10_ruling2_*` tests for the regression coverage.

- **2026-08-23, PR #15 (third entry — same PR, follow-up review round):** the PR was approved with one non-blocking recommendation, which was taken immediately (same slice) rather than deferred: **Ruling 3 — split the single, mode-dependent `ff_flare_dismiss()` into two explicit, intent-aware functions**, `ff_flare_dismiss_takeover()` (clears a pending takeover only, no effect on the lock) and `ff_flare_release_lock()` (releases the navigation lock only, no effect on a pending takeover). Reviewer's concrete repro: with double-duty `dismiss()`, a user tapping "stop navigating" at the exact instant a new flare's takeover arrives silently gets routed into the takeover-dismiss branch — the user's actual intent (release the lock) is dropped, *and* the new takeover is swallowed unseen (never shown, never decided). A mode-dependent API can't distinguish those two intents; only the caller knows which one it meant. Rationale for taking this now rather than deferring: nothing in this repo calls `ff_flare_dismiss()` yet (slice b/UI wiring hasn't started), so this is a pure addition-then-removal with zero call sites to update — done after slice b existed, this would have been a breaking `[api]` change against real call sites instead. `test_flare.c`'s `S10_ruling3_*` tests cover both split functions' independence, including the reviewer's exact race case (`S10_ruling3_release_lock_while_takeover_pending_keeps_takeover_visible`: takeover pending + `ff_flare_release_lock()` called → lock released, takeover still pending and still visible).

- **2026-08-23, issue #27 / PR #41 (takeover disclosure chip — wording, not substance).**

  **Provenance first, because the first draft of this entry got it wrong.** The requirement that the takeover screen disclose what pressing GO costs comes from **PR #20's UX review, BLOCKING finding #3 — "GO must disclose what it costs"** — the source `ff_flare_fmt_go_switches_lock`'s doc comment already cites. It does **not** come from Ruling 2 above, which is entirely state-machine semantics: that a newer flare never touches an existing lock, that DISMISS returns to the intact lock, that GO is the explicit decision that switches it, and that the locked node must be a fact the user chose. Ruling 2 is why an established lock is the user's decision to make; finding #3 is why the screen has to say what that decision costs. PR #41's code review caught this amendment (and `flare_fmt.h`) attributing the second to the first. Corrected here, because the whole purpose of writing the requirement down is that a future re-wording can be checked against it — and a citation pointing at a paragraph that does not contain the requirement is worse than no citation at all.

  **What shipped.** The chip is `GO DROPS LOCK - DANA` at 20px (`ff_flare_fmt_lock_cost`, `app/screens/flare_fmt.h`). It replaces PR #20's `LOCKED ON DANA - GO SWITCHES TO KEV` (36 characters, two clauses, 14px chip type) — legible and correct, but a *read* rather than a *glance* on the one screen that interrupts the user mid-panic at 2 AM, which is what issue #27 was opened to fix.

  **The route there is worth recording, because the obvious short form was wrong.** PR #41's first pass shortened it to `GO: DANA → KEV`, which carried every fact but failed in a way that is easy to reproduce and hard to see from a desk: shortening had deleted the sentence's **verb**, and the verb was the disclosure. `A → B` means *via* or *then* in every context a person meets it outside this app — breadcrumbs, file paths, map directions — so the chip read as an itinerary ("go to Dana, then Kev"), i.e. as **keeping** the lock. It also deleted the word **LOCK**, which is the only vocabulary the user has for this concept: the Radar face's own chip reads `LOCKED - DANA`, and the takeover screen had stopped connecting to it. Constraints for any future re-wording, in order:
  1. **A verb of loss is mandatory.** A glyph, an arrow, a colon or any other punctuation cannot carry "instead of" — those all read as sequence.
  2. **The word LOCK (or LOCKED) stays**, and the ` - <name>` tail matches the Radar face's lock chip, so the two chips visibly belong to each other.
  3. **The incoming sender is deliberately NOT on the chip.** It is the takeover's 22px headline directly above, built unconditionally by the same function that builds the chip. Naming them twice spends the chip's entire width budget on the largest thing already in view. This split is only honest while the headline exists, so it is pinned by `S10_ACn_lock_disclosure_is_always_accompanied_by_the_headline` rather than left as a convention.

  **Name truncation** is `FF_FLARE_FMT_LOCK_NAME_MAX` = 11 **bytes**, with an explicit `...` suffix. `FF_APP_NAME_LEN` permits 15, and a 15-character name at 20px puts the chip's corner 244.5px from the puck centre against a radius of 220 — off the round glass. The cap was chosen by measuring the rendered chip, not by arithmetic (13 is the failure threshold at -8.6px; 11 leaves +14.2px); see the macro's doc comment for the full table. **The ellipsis is not decoration.** PR #41's first pass truncated at 9 with a bare `%.*s`, and because the chip then carried *two* names, ALEXANDRIA-locked / ALEXANDRINA-flaring rendered as `GO: ALEXANDRI → ALEXANDRI` — a trade of a person for themselves, which reads as "this costs nothing, press GO", the precise outcome finding #3 exists to prevent, produced by the mechanism meant to enforce it. The single-name wording makes that failure inexpressible (there is no second name to be equated with) and the wider budget renders that exact pair whole; the ellipsis guarantees the weaker floor in every remaining case — a cut name always *looks* cut. Truncation is by bytes, backing off to the last complete UTF-8 codepoint, since crew names arrive as untrusted UTF-8 off the radio.

  **One glyph note that is now historical but worth keeping**, because the constraint it checked is real and will come up again: `→` (U+2192) is *not* in the compiled Montserrat subset (text range `0x20-0x7F`, `0xB0`, `0x2022` — the same gap that forced U+00B7 MIDDLE DOT into a hyphen across this codebase), but LVGL's built-in FontAwesome range *is* compiled in, and `LV_SYMBOL_RIGHT` (61524 / `0xF054`) is present in every Montserrat size this repo enables — verified at the compiled-font level, not from the generator comment. The glyph rendered correctly. It was still the wrong design, which is the lesson: coverage was answerable and answering it did not make the arrow mean "instead of". The shipped wording uses no symbol glyph at all.
