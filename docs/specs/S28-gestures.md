# S28 — On-glass navigation gestures (edge-swipe BACK / HOME, long-press flare)

## Why
The printed case's physical home/BOOT cap is unreliable (Jake, on-glass 2026-09-04). Touch is reliable. Give BACK and HOME a touch path that cannot collide with scrolling. History to respect: PR #130 fixed "scrolls accepted as swipes" (a vertical top-swipe to Map ate list scrolls); S26 slice e then retired the swipe carousel entirely — `scr_nav.c` no longer emits `FF_INTENT_SWIPE` and the tileview's gesture machinery must stay untouched (tiles `LV_DIR_NONE`, no `LV_DIR_HOR`, no re-enabling LVGL GESTURE routing). S28 adds gestures that are gated on WHERE the touch starts (rim zones) and on axis lock, recognised mid-drag from raw indev points, not from LVGL's GESTURE events.

## Gestures (display-space pixels, 412×412, glass circle centre (FF_THEME_GLASS_CX, FF_THEME_GLASS_CY) = (208,206), radius FF_THEME_GLASS_R = 200; use the theme constants, flip-aware helpers `ff_theme_glass_cx/cy(flip)` if they apply to touch space — check how touch coordinates are flipped and use the same space the screens hit-test in)
- G1 BACK — touch DOWN inside the glass circle AND within the LEFT rim zone (x ≤ cx − r + 28), then the finger travels dx ≥ +56 px within 500 ms of DOWN, with |dy| ≤ 0.6·dx at the moment dx reaches 56, and with axis lock: if |dy| exceeds 24 px before dx reaches 56, the gesture aborts for this touch (it is a scroll). Recognised mid-drag; emits BACK once; nothing else for the rest of that touch.
- G2 HOME — touch DOWN inside the circle AND within the BOTTOM rim zone (y ≥ cy + r − 28), then dy ≤ −64 px within 500 ms with |dx| ≤ 0.6·|dy| and axis lock (|dx| > 24 before |dy| reaches 64 aborts) and mean speed ≥ 0.25 px/ms. Emits HOME once.
- G3 LONG-PRESS FLARE — on the RADAR face only: DOWN anywhere inside the circle on a NON-interactive object, held ≥ 1200 ms with total movement ≤ 12 px → emits QUICK_FLARE (same countdown/cancel takeover as the 5-tap `FF_INTENT_QUICK_FLARE` path; same sounds). Recognised from a tick, not release. Interactive = objects created through `ff_scr_button_create` (scr_nav.c) — tag them with `LV_OBJ_FLAG_USER_1` there (one place) and refuse G3 when the press target or any ancestor up to the face root carries USER_1. If a legacy long-press→OPEN_SETTINGS hook still exists on any face, remove it (Settings lives in the launcher now).
- A touch that starts outside the rim zones can never become G1/G2. A touch that starts in a rim zone but moves the other axis first is a scroll and is left alone. Gestures are ignored entirely while a takeover is active (FLARE, POWER_MENU) and while the wake-only touch gate is swallowing the first touch after wake (feed the FSM only from touches the shell would deliver as input).

## Semantics of BACK (extends the existing `FF_INTENT_BACK`, mark PR2 title `[api]`)
Handled in the shell in this order: (1) modal COMPOSE up → pop it (existing); (2) INBOX with a thread open → same effect as `FF_INTENT_INBOX_CLEAR_TARGET` (back to the list); (3) SETTINGS on a sub-page → back to the settings root page; (4) any other base face → same as `FF_INTENT_HOME` (launcher); (5) LAUNCHER → no-op. HOME is the existing `FF_INTENT_HOME`. Recognised BACK/HOME play the UI tick sound (respect `ui_ticks`).

## Core module (PR1, Tier 3): `firmware/core/include/ff_gesture.h` + `firmware/core/src/ff_gesture.c`, pure C11, no I/O, no LVGL.
```c
typedef enum { FF_GESTURE_NONE = 0, FF_GESTURE_BACK, FF_GESTURE_HOME, FF_GESTURE_LONG_PRESS } ff_gesture_kind_t;
typedef struct { int16_t cx, cy, r; int16_t rim_px; int16_t back_travel_px, home_travel_px; int16_t axis_lock_px; uint16_t window_ms; uint16_t long_ms; int16_t long_slop_px; bool long_press_enabled; } ff_gesture_cfg_t;
void ff_gesture_cfg_default(ff_gesture_cfg_t *cfg, int16_t cx, int16_t cy, int16_t r);  /* 28, 56, 64, 24, 500, 1200, 12 */
typedef struct { ff_gesture_cfg_t cfg; /* FSM state: phase, x0,y0,t0, last x,y, done flag, zone */ ... } ff_gesture_t;
void ff_gesture_init(ff_gesture_t *g, const ff_gesture_cfg_t *cfg);
void ff_gesture_set_long_press(ff_gesture_t *g, bool enabled);      /* glue flips this per active face */
ff_gesture_kind_t ff_gesture_feed(ff_gesture_t *g, bool down, int16_t x, int16_t y, uint32_t now_ms); /* every DOWN/MOVE/UP sample */
ff_gesture_kind_t ff_gesture_tick(ff_gesture_t *g, uint32_t now_ms);  /* long-press timing; returns LONG_PRESS at most once per touch */
```
Wrap-safe time via `ff_time_reached` (ff_clock.h). At most one recognition per touch; after recognition the FSM is DONE until UP. Unit tests (Unity, ctest, names `S28_AC<n>_...`): AC1 left-rim swipe → BACK exactly once; AC2 same motion starting 40 px inboard → NONE; AC3 vertical scroll starting at the left rim → NONE; AC4 slow swipe (600 ms) → NONE; AC5 bottom-rim swipe up → HOME; AC6 diagonal beyond the ratio → NONE; AC7 long press 1200 ms with slop ≤ 12 → LONG_PRESS from tick, with 20 px movement → NONE, disabled flag → NONE; AC8 no second event after recognition until UP; AC9 DOWN outside the glass circle (a corner pixel) never starts a gesture; AC10 time wrap around 0xFFFFFFFF still recognises. ## Amendment (2026-09-07) — BACK/HOME unreachable on the Map face: a stalled poll loop, and a stall-tolerant window

**Bench evidence** (real puck, sample log from the gesture glue; times relative to DOWN). Radar face: `DOWN(5,187)` then samples at +16, +36, +56 … +176 ms (dx +68) → BACK recognised. Works. Map face: `DOWN(5,177)` then the FIRST poll sample at **+523 ms**, next +543, +563; another Map touch `DOWN(5,190)`: first sample +523 ms, dx +34 at +543 ms, +82 at +623 ms, +150 at +663 ms → never recognised, because the 500 ms recognition window (measured from DOWN) had already expired before any sample arrived. A third Map touch `DOWN(371,270)`: first sample +527 ms. Pressing the Map screen stalls the LVGL timer (touch poll + gesture tick) for ≈ 520 ms on EVERY touch, regardless of where on the glass it lands — and since BACK/HOME are the only way off the Map (it has no buttons of its own), the user is stuck there.

**Root cause — the Map's own render cost, not the gesture FSM.** `scr_map.c` drew every polygon fill triangle and every stroke segment as its OWN full-puck-sized `lv_obj_t` (a real widget: its own event list, style array, spec_attr/children bookkeeping) carrying a one-primitive `LV_EVENT_DRAW_MAIN` callback — this file's own pre-existing header comment already named the resulting scale ("up to ~300 full-puck-sized triangle/segment proxy objects", the same object count issue #75 separately flagged as a `clip_corner` hang risk). For a real, fully-populated festival pack this is genuinely in the hundreds of `lv_obj_create` calls, each with real per-object overhead (heap allocation, event-list init, style-array init) — cheap once, but expensive to redo, and expensive relative to Radar's own handful of objects (an arrow + a few chips), which is why only the Map shows this stall. `firmware/app/screens/scr_map.c` was rewritten to append triangle/line draw data to a small array instead (a `map_draw_op_t` pool) and replay it through a shared `lv_obj_t`'s single draw callback — opened lazily and closed/reopened around each STAGE's own stub circle (kept as its own object; a from-scratch reimplementation against raw `lv_draw_rect` was tried and was NOT pixel-identical to `lv_obj`'s own bg+border draw, caught by `run_goldens.sh`) so the true creation-order z-order is preserved exactly. Verified against the real Lost Lands pack (`firmware/tests/fixtures/map_real_lost_lands.json`): the Map's rendered object count drops from tens of objects per polygon feature (a 9-point "Venue extent" alone used to cost 16 — 7 fill triangles + 9 stroke segments — one per feature, every feature) to **22 total objects for the whole Map tile** (shapes, labels, YOU arrow, crew, chrome — everything). All 90 golden fixtures render byte-identical (`0/169744` pixels differ) before and after; see `firmware/app/screens/scr_map.c`'s own header comment on `s_draw_ops` for the full mechanism and the two golden regressions an earlier version of this fix caught (`map_clip_stress`, `map_real_lost_lands`) before the z-order-preserving design was reached.

**FSM robustness (ff_gesture.c/.h) — stall-tolerant window, defense in depth.** Even with the Map's render cost fixed, ANY sufficiently slow device tick (a future heavy face, a busy moment, a slow frame under load) could still stall the touch-poll loop past the 500 ms window and make BACK/HOME briefly unreachable — the FSM itself had no way to tell "the device was frozen" apart from "the finger genuinely took too long". New rule, checked ONCE per touch, at the very first sample fed after DOWN (never re-applied to any later sample): if that first sample arrives more than `stall_gap_ms` (150 ms, new `ff_gesture_cfg_t` field, defaulted in `ff_gesture_cfg_default`) after `t0` (DOWN's own timestamp), the window's own clock (`t0`) is moved forward to that sample's timestamp — every subsequent `window_ms`/ratio/speed check (G1 BACK and G2 HOME both read `t0`) is then evaluated against the adjusted start. The touch's spatial origin (`x0`/`y0`, and therefore every `dx`/`dy` this FSM computes) is never touched — only the window's clock moves, never where the finger physically started. A gap `<= stall_gap_ms` (the ordinary case) changes nothing. See `ff_gesture.h`'s own "Stall tolerance" section for the full mechanism and its own proxy-guard reasoning.

New unit tests (`firmware/core/tests/test_gesture.c`, mirroring the existing `S28_AC<n>` convention — see that file's own header comment for a numbering caveat: slice b's sim-level tests already use `AC11`–`AC18` for different, later criteria; these two are core-level and were named `AC11`/`AC12` per this amendment's own brief regardless, a real collision in the spec's AC numbering flagged rather than silently avoided):
- **AC11** — a 520 ms poll stall after DOWN on the left rim, then a normal 56 px swipe within 500 ms of the FIRST sample (not of DOWN) → BACK. Mutation-proven: disabling the stall check (`git diff` / fresh build) makes this fail (`Expected 1 Was 0`) while every other test, including AC12, still passes.
- **AC12** — a genuinely slow swipe (a prompt first sample establishing "not stalled", then 56 px only after 700 ms — over the 500 ms window) → NONE. The tolerance is for GAPS, not for slowness in general; this is the negative control against the proxy "a stall-tolerant window recognises a late swipe" (which a naive "just extend window_ms" fix would also satisfy, wrongly, for an ordinary slow drag).
- Existing **AC4** (slow swipe, 600 ms → NONE) was updated to feed a prompt first sample (20 ms, under `stall_gap_ms`) before its own 600 ms jump — its ORIGINAL two-sample shape (DOWN, then one sample 600 ms later) is, from the FSM's own perspective, indistinguishable from a genuine 600 ms device stall, and the amended FSM now correctly (not wrongly) rescues that exact shape; AC4's own intent — a slow finger on a live, unstalled poll loop — needed an explicit "not stalled" sample to stay unambiguous under the new rule.

## Amendment (2026-09-07, second pass) — map/home gestures still unreachable after the above; edge-tolerance fix + rim widening

**Bench evidence** (real puck, PR #228 build — commit `3b6bce7`; `(dx,dy)` relative to DOWN, times ms after DOWN, poll period 20 ms):

1. Radar, `DOWN(5,175)`: samples out to `+176ms(+137,+32)`, with `dx` first reaching 58 (`dy`=3) at `+136ms` → **NOT recognised**. Reported as a regression against pre-#228 behaviour.
2. Map, `DOWN(5,219)`: `+327ms(0,0) +347ms(+96,-20)` → **BACK recognised** (stall rule working as intended).
3. Map, `DOWN(5,180)`: samples out to `+176ms(+167,+69)`, `dx` first reaching 56 (167) at that same sample, ratio 69/167=0.41 ≤ 0.6 → **NOT recognised**. Suspected same-sample axis-lock-vs-threshold ordering bug.
4. Map, `DOWN(5,156)`: `+325ms(0,0) +345ms(0,+18) +385ms(+191,+103)`, ratio 103/191=0.54 ≤ 0.6 → **NOT recognised**. Same suspected ordering bug.
5. Map, `DOWN(5,207)`: `+56ms(+2,-36)` → correctly **NONE** (vertical-first, axis lock).
6. HOME attempts starting at `y=358` never recognise (358 < the then-current bottom-rim threshold of 384) — the puck's touch calibration compresses the bottom edge; a fingertip's reported centre sits well above the true glass edge there.

**Investigation.** Bullets 1–5 were reproduced and traced directly against the shipped `ff_gesture.c` (both `3b6bce7` and its pre-amendment parent `6174eaf`), using the geometry implied by items 5/6's own stated numbers (`cx=cy=206, r=206` — the only geometry under which "current left rim zone x≤28" and "bottom rim zone y≥384" both fall out of the standard `cx-r+rim_px` / `cy+r-rim_px` formulas with `rim_px=28`).

- **Item 3 and item 4 (suspected axis-lock ordering bug): NOT REPRODUCED.** `ff_gesture_feed`'s G1 block only evaluates the axis-lock check inside the `dx < back_travel_px` branch; the sample where `dx` first reaches/exceeds the threshold goes straight to the ratio+window `else` branch and never touches axis-lock at all — this was already the shipped behaviour, verified by direct compile-and-run of both sequences against `3b6bce7` unmodified: both return `FF_GESTURE_BACK` at the expected sample. No ordering fix was needed. Kept as regression guards (`S28_AC14`, item 3; folded into `S28_AC15`, item 4, alongside the real fix below).
- **Item 1 (suspected stall/t0 bookkeeping bug): NOT REPRODUCED.** Every inter-sample gap in this trace is ≤20ms — well under `stall_gap_ms`(150) — so the stall-tolerance rule never engages; `t0` never moves from DOWN's own timestamp. Verified against both `6174eaf` (no stall-tolerance code at all) and `3b6bce7`: both already return `FF_GESTURE_BACK` at `+136ms`. No bug found in this module for this exact trace; kept as a regression guard (`S28_AC13`). If the real device genuinely failed to recognise this motion, the cause is outside `ff_gesture.c` (most likely the production glue/indev delivery path, or a geometry mismatch between the bench capture and the puck's actual runtime `cx/cy/r` — not something reproducible in the core FSM without contradicting this direct evidence).
- **Item 4: a REAL, reproducible bug, found during this investigation.** `DOWN(5,156)` is `dist ≈ 207.13px` from `(206,206)` — `≈1.1px` OUTSIDE the admission circle (`r=206`). Before this amendment, `gesture_in_circle` compared against `r` with zero tolerance, so this entire touch was `FF_GESTURE_PHASE_ABORTED` at DOWN — before the stall check, rim zone, axis lock, or ratio logic ever ran. This is the SAME touch-calibration phenomenon item 6 already documents for the bottom (HOME) rim, but here it blocks admission outright, for BACK. **Fix**: new `ff_gesture_cfg_t` field `edge_slop_px` (default 16), used only by the admission (`gesture_in_circle`) check — `dist² ≤ (r + edge_slop_px)²` — leaving `r` itself, and every rim-zone formula that uses it, exactly as precise as before. Mutation-proven: reverting `gesture_in_circle` to compare against plain `r` makes `S28_AC15`'s first assertion fail (`ABORTED` instead of `TRACKING`) while every other test still passes.
- **Item 6: rim zones widened as directed.** `rim_px` (previously one shared field, pinned at 28 for both G1 and G2) is split into `back_rim_px` (default 44) and `home_rim_px` (default 64). `S28_AC2` updated: the "just inboard of the zone" negative-control point moves from 40px inboard of the (now-wider) edge to 60px inboard, keeping the same "comfortably outside the zone" margin the original test intended.

**New core-level tests** (`firmware/core/tests/test_gesture.c`, bench geometry `cx=cy=r=206` throughout this section, kept distinct from the file's existing `GLASS_CX/CY/R=208/206/200` convention used by AC1–AC12):
- **AC13** — bug (1) replay (Radar swipe). Passes on unmodified `3b6bce7`; a regression guard, not a fix.
- **AC14** — bug (3) replay (Map, same-sample ordering). Passes on unmodified `3b6bce7`; a regression guard, not a fix.
- **AC15** — bug (4) replay (Map, edge-of-glass DOWN point). **Fails on unmodified `3b6bce7`** (`ABORTED`, not `TRACKING`); passes with the `edge_slop_px` fix. The one test in this section that required an actual code change.
- **AC16** — bug (2) replay (Map, the bench's own positive/stall-only control). Passes throughout (already covered in spirit by AC11/AC12; kept here for completeness of the bench replay).
- **AC17** — bug (5) replay (Map, vertical-first stays NONE). A negative control proving the edge-slop and rim-widening fixes did not loosen the axis lock.

**Gates**: `cmake -S firmware -B build -DFF_TARGET=sim && cmake --build build -j8 && ctest --test-dir build --output-on-failure` (clang, AppleClang 21.0.0) — 74/74 passed, zero warnings. Same under `CC=/opt/homebrew/bin/gcc-14` (GNU 14.4.0) — 74/74 passed, zero warnings. `firmware/tests/run_goldens.sh` — all 90 fixtures pass under both build trees, byte-identical (`0.0000%` diff on every fixture).
